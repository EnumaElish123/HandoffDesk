# HandoffDesk Linux 实际试用记录与优化方案

- 日期：2026-10-29（Asia/Shanghai）。
- 对象：HandoffDesk 0.10.0，Git 提交 `3065b48e2a60523772db9618e4ec90c588d1fdd2`。
- 目标：检验“安装一次，Agent 自主记录并逐次汇报，用户主要通过 Linux TUI 阅读”的完整体验。
- 本轮交付：实际操作记录、问题证据、优化设计、实施顺序与验收标准。**本轮未修改产品代码，以下优化尚未实施。**

## 1. 结论

Linux 端已经能够保存和阅读真实进展，原有项目与历史也能正常显示。现阶段主要缺口集中在安装后入口、跨轮次续接、任务发现及终端阅读状态：用户仍可能需要理解状态目录、会话编号、轮次和终端焦点，尚未达到“安装后主要阅读即可”的体验。

本轮归并出 **14 项问题：3 项 P1、10 项 P2、1 项 P3**。优先处理升级时默认记录目录改变、已结束任务恢复的状态错误、安装成功后找不到入口，然后补齐 Agent 任务发现与终端阅读链路。没有观察到旧历史被删除；“项目消失”复现的是默认入口切换到其他状态目录。

已验证的基础能力应保留：稳定回执与幂等重试、附件校验、失败提案留存、并发冲突保护、保存与汇报/已读状态分离，以及刷新时保留当前详情。

原始证据保存在仓库忽略的 `work/linux-trial-20261029/`，其中可能含本机路径。本文仅保留必要结果及可复现步骤，不复制个人项目内容。SVG/PNG 是应用布局快照，字体替换可能造成浏览器中的中文显示失真；**没有据此判定真实终端存在字体重叠缺陷**。

### 2.2 三个场景

**场景 A：继续维护 HandoffDesk 本身（真实项目）。**

1. 用户打开 Linux TUI，检查已有项目、历史和上一轮开发记录的附件。
2. Agent 对当前工具开展本次试用，整理本报告。
3. Agent 将本报告作为附件保存到原有 HandoffDesk 项目，并逐次汇报回执。
4. 用户侧再次通过 TUI 搜索该记录、阅读详情和预览本报告，完成真实读写闭环。

**场景 B：夜间导出告警排查（受控业务案例）。**

建立中文/空格路径的项目和一份含两日数据的 CSV：分别为 3 单/125 元、4 单/165 元。Agent 计算合计 7 单/290 元，写出排查文档，并明确“时区边界尚待复核”；随后保存、汇报、交接、次日继续，以及模拟中断、附件缺失后恢复和并发写入。不存在真实生产事故，此案例用于检验有实际文件和可核对结论的交接流程。

**场景 C：同一项目并行处理两个任务（受控阅读案例）。**

“接口超时排查”和“发布说明核对”各写一条同名阶段“完成第一轮核对”，让用户只凭记得的任务名称找回进展；再检查未读、长正文、附件、搜索与自动刷新。另生成明确标注的 55 条合成历史，用于检验多页浏览；这些不计作真实项目成果。

## 4. 逐项复现与优化设计

### L01：升级不能让既有记录从默认入口消失

**复现条件：未指定 `--state-dir`，使用 `--no-connect` 重装。** 在独立环境创建自定义状态目录，接入后将安装登记指向它；不带 `--app-dir` 查询能看见 1 个项目。按文档运行 `python scripts/install.py --no-connect`，不另填路径，安装退出 0。再次从相同便携版入口查询得到 `[]`；显式指定原目录后项目仍在。

**原因。** `scripts/install.py` 独立计算平台默认目录，随后重写安装登记，没有沿用 `handoffdesk/paths.py::app_directory` 的环境变量/既有登记解析规则。实测是目录选择错误，未观察到删除；未另行实测启用自动接入的重装路径。

**方案。** 统一状态选择：显式 `--state-dir` → `HANDOFFDESK_HOME` → 当前安装登记 → 平台默认。升级默认沿用记录目录；切换目录是独立、明确的迁移操作。对损坏登记显示错误，不以空目录自动覆盖。安装结束显示“已沿用已有记录”和所用目录，低层路径放在详情中。

**验收。** 自定义目录、环境变量、平台默认、损坏登记分别覆盖；升级前后项目及历史 ID 一致。未显式迁移时不得更改既有状态位置。

证据：`onboarding/upgrade-before-list.json`、`upgrade-default-install.json`、`upgrade-after-list.json`、`upgrade-after-custom-list.json`。

### L02：统一继续任务与恢复轮次的语义

**最短复现链。** 下列命令均选择同一隔离状态，`S/T/K/R` 为真实命令返回值：

```text
agent begin --cwd CASE --task 排查夜间导出告警       -> S、T、K
agent checkpoint --session S --checkpoint K ...  -> R1
agent ack-report --turn T --receipt R1 ...
agent conclude --turn T --outcome recorded --receipt R1 -> 退出 0
agent resume --session S                          -> 退出 0，仍是 T
agent checkpoint --session S --checkpoint 新令牌 ... -> R2，保存成功
agent conclude --turn T --outcome recorded --receipt R1 --receipt R2
                                                  -> 退出 2，turn_concluded
```

新成果确实保存，但沿用了已结束轮次。`paused` 后普通 `resume` 也返回成功并沿用旧轮次，之后保存被拒绝。对照试验中，固定同一受控宿主 ID 再次 `begin` 能复用 session 并建立新轮次，流程正常；因此不是所有续接都失败。

**原因。** `agent_session.py::resume` 只为 interrupted/failed 创建恢复轮次；`checkpoint` 允许向 recorded 轮次写新记录，最终被 `conclude_turn` 的不可变规则拒绝。入口状态转换不一致。

**方案。** 继续已完成任务时保留 session/workline，建立新的工作轮次；中断/失败则建立关联恢复轮次。暂停必须有明确“恢复记录”意图，普通查询不能解除暂停。拒绝向所有已结束轮次追加新记录，但继续允许成功令牌原样重放。返回结构应直接给出是否可写、原因及下一动作。

**验收。** 完成 → 次日继续 → 保存 → 汇报 → 结束全部成功；旧轮次及回执不改写；暂停未经明确恢复不可写；中断/失败的补救预算与待汇报项仍保留。

当前已验证的人工绕行是 `observe --resume-of` → `resume --turn`，但不宜要求普通用户或 Agent 默认自行拼出这组内部操作。

证据：`agent/06_conclude.json`、`07_resume_completed.json`、`08_checkpoint_after_conclusion.json`、`10_conclude_continued.json`、`host-comparison.json`。

### L03：安装完成必须给出立即可用的阅读入口

**复现。** 真实源码安装退出 0，但在隔离的常规系统 PATH 执行 `handoffdesk feed` 返回 127 / command not found。实际入口位于 `~/.local/lib/handoffdesk/handoffdesk`，用绝对路径可用；安装结尾只有完成和 hooks 信任说明，没有可复制启动命令。新安装 TUI 的 PTY 启动、`q` 退出均成功，问题不是程序无法运行。

**方案。** 在 `~/.local/bin` 建立归本安装管理的入口，检查 PATH 和同名命令冲突。无论 PATH 是否可用，都输出正确转义的绝对启动命令；不要求用户先编辑 shell 配置。不要覆盖其他来源的同名命令。升级/卸载仅管理自己创建的入口。

**验收。** 安装完成后直接复制一条命令即可阅读；用户命令目录已在 PATH 时，新终端直接运行 `handoffdesk`；中文/空格安装路径、旧入口、同名外部命令均有明确行为。

证据：`onboarding/installer-real.json`、`command-after-install.json`、`owned-launcher-feed.json`。修改点：`scripts/install.py`。

### L04：让 Agent 能从工作目录发现需要续接的任务

**复现。** 不提供宿主会话 ID，同 cwd、同 task 再执行 `begin`，返回不同 session/workline、`resumed=false`、空 history。`agent status` 不带 session 退出 2；帮助中没有按目录发现会话的命令。旧内容仍存在，但新 Agent 失去聊天上下文后没有直接找回入口。

**方案。** 增加 `agent sessions --cwd ...` 或等效发现接口，返回稳定任务 ID、名称、最新阶段、未完成事项和推荐动作；显式区分“继续已有任务”和“新建任务”。同名不等于同一任务，存在多个候选时不得默默合并。Skill 在新上下文先查任务，用户只需表达继续什么工作；TUI 可复制“继续此任务”的简短指令。

**修改范围。** `workspace.py`、`agent_session.py`、`agent_session_cli.py`、Skill 模板；保持原 session/workline ID。

**验收。** 仅凭 cwd 即能发现候选；续接不额外制造同名工作线；明确新建仍可保留同名独立任务；并行任务和 Git worktree 不错绑。此项与 L02 一起完成，避免“找得到但恢复失败”。

证据：`agent/11_begin_same_task.json` 等编号 11–13 的调用、`summary.json`、`25_feed.json`。以目录中的 `transcript.json` 为实际文件名索引。

### L05：默认恢复信息应短小且足够行动

**实测。** 每阶段正文 1,279 字符，全部正常确认汇报，`pending_reports=0`：

| 已保存阶段 | `status` 标准输出 UTF-8 字节 | 本机单次耗时 |
| --- | ---: | ---: |
| 1 | 15,954 | 149.73 ms |
| 10 | 119,050 | 200.94 ms |
| 50 | 535,774 | 207.22 ms |

这不是 token 数量，也不是跨系统基准。主要问题是 Agent 上下文占用；没有据此声称本机执行明显变慢。

**原因。** `status` 同时返回最近 history、最多 100 个 checkpoint 的 request 与 receipt，其中重复包含正文；`resume` 直接返回同一结构。

**方案。** 默认返回当前令牌、任务/轮次状态、最新阶段摘要、待保存项、待汇报摘要及下一动作。原提案、单条回执和完整历史通过明确参数按需读取；历史分页。错误恢复所需的完整内容必须仍可取得，不能为减小输出而丢弃。

**验收。** 50 条约 1,300 字的已汇报历史下，默认响应建议不超过 8 KiB；完整单条可恢复，待处理项无遗漏，幂等性不变。该阈值是拟定目标，不是当前能力。

证据：`agent/scaling-metrics.json`、`62_size_status_*.json`。

### L06：用户记得的是任务，列表与搜索应围绕任务组织

**复现。** 同一项目有“接口超时排查”“发布说明核对”两个任务，两条阶段标题都为“完成第一轮核对”。列表只显示标题、项目和分钟时间，看起来相同；没有任务筛选。搜索“接口超时排查”得到 0 条；搜索任何正文均未出现的 `last_done` 却得到 2 条。

**原因。** TUI 列表不显示 `workline_name`；`reader.py::records` 对整段 JSON payload 做 LIKE，工作线名称不在该 payload，而内部键名参与匹配。

**方案。** 列表展示任务名称，增加轻量任务筛选或按任务分组。明确搜索可见字段：项目/任务名称、标题、完成内容、下一步、阻碍、附件名/用途；不把内部键名当用户内容。普通本机规模先做正确的字段检索，是否引入全文索引由数据量测量决定。

**验收。** 不打开详情就能区分两个任务；正文/路径未出现的任务名仍可搜到；`last_done` 只有在用户内容确实写入该词时才命中；中文片段及 `%`、`_` 行为可预期。

证据：`tui/results.json` 的 `task_discovery`、`search_task_title`、`search_internal_key`；Agent 侧 25–28 的独立复现。

### L07：主动搜索后应显示搜索结果

**复现。** 80×24 打开详情，按 `/` 搜索一个不存在的词：状态显示“0 条记录”，正文仍是旧记录；详情可见、结果列表隐藏。详情中按 `u` 筛未读也保留旧的已读内容，必须自己想到 `Esc` 返回列表。

**原因。** 窄屏的 detail-mode 没有随主动搜索/筛选切换。为后台刷新保留详情的策略被沿用到用户主动更改条件。

**方案。** 区分主动操作与后台刷新。用户更改搜索、项目、任务或未读条件时，窄屏进入结果列表；零结果显示原因和清空条件动作。宽屏若保留原详情，应明确标注“当前详情不在筛选结果中”。后台到达新记录仍保持原阅读位置。

**验收。** 80×24 搜索后立即可见结果/空状态，不能把旧正文误当命中项；输入字母不触发全局快捷键；后台刷新不打断阅读。

证据：`tui/more-results.json::search_from_detail_zero_results`、`search-from-detail-zero-results.svg`。

### L08：刷新时保护已经加载的历史与选中项

**复现。** 首次 50 条，按 `n` 加载更多至 58 条；追加一条记录后仍显示 58 条，原最旧记录被移出已加载集合，需再次翻页。补测在 60 条集合中高亮最后一条：新记录到达后，高亮从索引 59 跳到 0，列表滚动从 105 跳到 0。

**原因。** `load_records(preserve_depth=True)` 保留的是已有条数，不是已加载历史边界；新记录占用前面的名额。先前选中 ID 被挤出后默认选中第一项。

**方案。** 保留选中 ID、顶部可视锚点和已加载最旧边界；新记录可增量插入并提示数量，或在用户离开顶部时暂存到“有 N 条新进展”入口。分页去重，不以新记录替换用户已加载的旧记录。大量更新时可设内存上限，但不可静默移除正在查看的项。

**验收。** 加载至少两页、选择最旧项后连续追加 10 条，选中 ID 和可视位置保持；旧项不消失、不重复；用户主动返回最新时才跳到顶部。

证据：`tui/more-results.json::pagination`、`edge-results.json::oldest_highlight_after_new_record`。这是列表位置问题；当前已打开详情的正文和滚动保留测试通过。

### L09：空状态说明现在处在哪一步

**复现。** 全新 TUI 只有“0 条记录”和“从左侧选择一条阶段记录”，没有可选记录、接入状态或下一步。用户无法判断 Agent 是否已接入。

**方案。** 区分未接入、已配置但未验证、等待第一条记录、当前筛选无结果四种状态。给一句原因和一个可执行动作。新增“接入与状态”页面，读取同一状态目录的接入信息；已配置情况下只提示让 Agent 做一件真实工作，不制造演示进展，不要求逐项目配置。能自动检测的路径由程序处理。

**验收。** 新用户不查仓库文档即可判断下一步；信任未验证不能显示“自动记录已就绪”；搜索无结果不能误导用户重新安装。

证据：`onboarding/empty-tui.json`、`empty-tui.svg`。修改点：`tui.py` 与现有 integration 状态接口。

### L10：诊断应解释当前阻塞，而非要求用户解释 JSON

**复现。** 隔离 PATH 中没有 Codex 命令，`connect codex` 退出 0，正确表示接入文件准备完成。`doctor --probe` 退出 2，`host.status=executable_unavailable`，权限探针正常；总提示却仍主要要求在实际 Codex 中再运行诊断，没有直接指出当前缺少可检测入口。

**边界。** `awaiting_host_trust`、`fully_verified=false` 的表述正确，不应改成只要文件存在就声称成功。没有 CLI 也不必然等于没有桌面宿主。

**方案。** 增加结构化 `issues[]` 和每项 `next_action`；给人阅读时显示“阅读可用、Skill 文件、宿主检测、hooks、信任、写权限”各层状态，并突出当前可执行下一步。保持 JSON 接口兼容，先增加 `--human` 或让 TUI 消费结构化诊断，避免直接改变 Agent 依赖的默认输出。

**验收。** 无 CLI、入口启动失败、hooks 未启用、权限不足、Skill-only 各有准确提示；不能把手动探针或 handler 日志当宿主信任证明；正常阅读不依赖 hooks 全部就绪。

证据：`onboarding/connect-missing-codex.json`、`doctor-before-connect.json`、`doctor-after-connect.json`。修改点：`integration.py::doctor`、`integration_cli.py`、TUI 状态页。

### L11：附件应优先给正文空间，并提示如何阅读

**复现。** 80×24 下仅 2 个附件，文件列表固定占 8 行，预览控件只有 7 行，路径/用途进一步占据正文空间。Enter 预览后焦点仍在文件列表，PageDown 不滚正文；Tab 后 PageDown 才滚动 5 行。60×18 下预览控件只剩 2 行边框，正文可视高度为 0。文件移动后列表未提前标缺失，进入预览才看到错误。

**方案。** 附件列表按条目数设置高度并有上限；小终端选择文件后切换到全文预览页，Esc 回附件列表。长路径放可展开元信息，始终保留完整路径复制能力。Enter 后聚焦预览或明确提示 Tab 切换。列表显示可用/缺失/文件夹状态；缺失时提供“请 Agent 更新关联”的说明或可复制指令，不要求用户理解内部文件 ID。实际关联修复应由 Agent 使用既有文件接口执行。

**验收。** 80×24 默认正文至少 10 行；60×18 仍能读正文或明确给出尺寸要求/CLI 回退，不能呈现零正文空间。PageDown 行为与提示一致；长中文路径可完整取得；缺失附件不崩溃，也不执行脚本。

证据：`tui/files-80x24.json`、`results.json::missing_attachment`、`edge-results.json`。修改点：`tui.py::FilesScreen`。

### L12：人类时间显示必须包含时区语义

**复现。** 记录保存为 `2026-10-29T01:11:57+00:00`，列表直接截成 `2026-10-29T01:11`，丢掉时区；Asia/Shanghai 用户对应当地时间为 09:11。详情保留完整偏移，但用户从列表无法判断。

**方案。** 存储继续使用 UTC；阅读层默认采用可检测的系统时区，并显示时区缩写或偏移。远程服务器时区可能与阅读者不同，因此提供可选显示时区，并始终能查看原始时间。无需为了正确显示要求所有用户先做设置。

**验收。** UTC、Asia/Shanghai、跨日及夏令时边界有明确展示；列表和详情一致；排序仍按真实时间/稳定游标，不按本地字符串排序。

证据：`tui/results.json::task_discovery` 与相应详情快照；修改点：`tui.py::load_records`、阅读展示格式。UTC 存储本身不是错误。

### L13：只保留一条清晰的 Linux 首次使用主路径

**复现。**

1. 非 TTY 的提示推荐 `feed` 或 `list --json`；在分别独立的全新状态，前者返回空列表，后者却要求 `init`。
2. 按 `docs/ubuntu.md` 源码流程执行 `init`，得到 `Demo project`；与 README 的空状态、自动登记项目相冲突。
3. 缺少 Textual 的真实 PTY 提示安装 `handoffdesk[tui]`，没有提供当前解释器/源码路径。仓库说明按源码安装、不假设 PyPI 发行；本轮未查询 PyPI，不能断言那里不存在包。
4. Ubuntu 服务器章节仍将协议 1 的 schema/context/validate/save 作为主要记录流程。

**方案。** 主流程统一为安装 → 一次接入 → Agent 记录 → TUI 阅读。手工项目登记、演示初始化、协议 1、旧 Tk 移至兼容章节。纯阅读 `list` 对无配置返回空，或至少修正推荐回退。缺组件提示根据来源给可执行修复命令：源码使用当前解释器和已知源码位置，便携版给正确重装方向。

**验收。** 逐字执行快速入门无需编辑项目配置，不产生 Demo；无 TTY 回退在新状态可用；修复命令匹配实际安装来源，兼容接口仍保留。

证据：`onboarding/portable-no-tty.json`、`portable-feed-empty.json`、`portable-list-empty.json`、`ubuntu-doc-init.json`、`missing-textual-pty.json`。

### L14：从当前详情直接导出

**观察。** README 将 TUI 与 Markdown 导出并列为能力；当前 TUI 快捷键/帮助中没有导出动作。导出能力存在于 CLI 的 `read RECORD_ID --markdown`，需要离开界面、取得长编号并重定向到文件。此项是入口缺口，不是声称底层导出失败。

**方案。** 为当前详情增加导出/复制摘要动作，默认给合理文件名，用户确认目标即可；CLI 继续提供机器可调用方式。附件仍是引用，不暗示导出包含文件副本。

**验收。** 在当前记录内完成导出并显示实际位置；已存在文件不静默覆盖；UTF-8 中文、验证信息、附件用途和完整路径保留；用户取消不报错。

证据：`tui.py::HandoffApp.BINDINGS/action_help`、`cli.py` 的 `read --markdown`；本次成果的 CLI 导出另存于 `work/linux-trial-20261029/`。

### R1 的具体实施顺序

1. 将安装器与运行时共用的状态定位抽成单一接口；保留显式覆盖行为，不进行隐式迁移。
2. 定义统一的“可写轮次/已处置轮次/明确恢复”转换，令 `begin`、`resume`、`checkpoint` 行为一致。
3. 用 L01/L02 最小复现作为回归检查；同时覆盖原有重放、中断补救和暂停保护。
4. 在自定义状态副本中实际执行升级，再完成两天同一任务的保存/汇报/结束。

### R2–R4 的实现约束

- 用户首页优先显示进展、下一步、阻塞与文件，内部 session/checkpoint/turn 编号放到详情或由 Agent 消化。
- 接入成功、保存成功、Agent 已汇报、宿主观察到、用户已读分别表达；不能用一个“成功”掩盖各层差异。
- 后台刷新保留阅读现场；用户主动搜索/切项目则优先展示新结果。
- 默认操作可用且少配置，发生歧义时让 Agent 或明确的用户选择解决，不静默猜测任务绑定。
- 安装与导出只管理本工具拥有的文件；不覆盖用户命令、旧历史、用户编辑的 Skill 或第三方 hooks。
- 优化界面不要求新装全局守护进程、数据库服务、X11 或浏览器；当前 SQLite 与终端架构足以先解决本轮问题。
