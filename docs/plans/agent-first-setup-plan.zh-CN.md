# HandoffDesk 低配置 Agent 接入与双平台阅读优化方案

状态：2026-10-28 用户已批准实施，并确认 Windows 改用本地 Web 桌面前端、Linux 使用 TUI。依据：对 HandoffDesk 0.9.0、提交 `ca368dc` 的实际试用与官方资料核查。下述验收项是交付门槛，完成情况须以测试报告为准。

目标是让用户安装并连接一次后，Agent 在工作中自动接入当前项目、保存有依据的阶段记录、立即汇报保存结果。用户在 Windows 图形窗口或 Linux 终端阅读器中查看进展、验证范围、下一步和阶段文件。配置、版本号、重试和状态定位由程序处理，事实与判断仍由 Agent 如实填写。

首期采用 **统一安装与状态定位、简化记录接口、用户级 Skill、受支持 Codex 的生命周期漏记检查、Windows 本地 Web 桌面前端与 Linux TUI 共用阅读查询逻辑**。MCP 和跨机器同步放到后续独立阶段。实现可以在保持接口语义和验收标准的前提下调整内部模块名称。

## 1 试用结论与优化依据

| 实测或已核对的现状 | 对目标体验的影响 | 首期处理 |
| --- | --- | --- |
| 四个正式项目可切换；原有一条历史交接及其四个附件可读、可用 | 记录和文件关联可以作为保留内核 | 不重写历史、项目 ID 或文件清单 |
| 两次独立试用保存成功；原样重试去重，旧版本提交被拒绝 | 可靠性基础已有，不需要另建一套保存协议 | 简化入口内部复用现有事务与幂等机制 |
| 按现有指南安全完成首次记录需八次调用；固定项目后续阶段约四次 | 安装位置、项目、工作线、版本及 JSON 规则都压在调用者身上 | 首次一次 `begin`，每阶段一次 `checkpoint`，程序内部校验并回读 |
| 试用提交有十个顶层字段，其中九个必填 | Agent 必须处理过多技术字段 | Agent 只提供实际进展、下一步、验证和文件用途 |
| 窗口能检测新记录，但需要点击更新；正在阅读的内容不会被抢走 | 保留阅读位置是优点，新记录入口可以更清楚 | 自动更新列表，明确提示新增；详情保持稳定 |
| Agent 新增第二个项目后，已打开窗口仍只显示原来一个项目 | 自动接入成功后用户可能看不到成果 | 同时监听项目配置和记录变化，无需重启 |
| 新项目显示“原有工作线”；首页材料列表可为空，但“本次文件”已有附件 | 空状态容易被误解为记录没有保存 | 普通阅读围绕已保存阶段，来源配置移入高级入口 |
| Markdown 导出缺少阶段文件清单、作者和验证范围 | 离开应用后交接信息不完整 | GUI、TUI、导出使用同一记录展示模型 |
| 当前没有 TUI；默认安装仍要求 Python 3.10+，桌面需要 Tk | Linux SSH 用户不能直接获得阅读界面 | Linux 发行包默认提供 CLI 与 TUI，无需图形环境 |
| 部分未初始化的 `--json` 命令返回纯文本错误 | Agent 需要按命令分支解析错误 | 新接口统一结构化错误、修复动作和退出状态 |
| 旧接入授权路径可能与迁移后的状态目录不一致 | 安装器能运行不代表实际 Agent 能写入 | 在真实宿主权限环境执行可撤销接入探针 |

本次 GUI 检查在 Linux 独立图形会话进行，不代表 Windows 真机验收。正式历史记录与启动前一致；窗口正常自动刷新使来源快照由两份增至八份，也更新了阅读偏好。两个原有占位项目的来源缺失属于尚未接入的状态。试用附件点击“打开”后显示“已请求打开”，但没有出现可读文档窗口；本轮确认了附件存在、用途、路径复制与阶段追溯，外部文档打开仍需原生平台验收。

## 2 用户最终需要做什么

### 一次安装和连接

1. Windows 运行安装包；Linux 运行用户级安装入口。发行包自带经过验证的运行时与对应阅读依赖，用户无需配置 Python、Tk、虚拟环境或环境变量。
2. 选择“连接 Codex”，安装器探测宿主与执行机器，安装本工具的 Skill 和可用接入项。安装器完成环境、状态目录及真实宿主读写检查。
3. 完成 Codex 要求的首次 hook 信任；只有实际探针通过，才显示“自动记录已就绪”。没有相关能力或未信任时，明确显示“仅 Skill 模式”或待完成步骤。
4. 此后正常给 Agent 分配项目工作，无需逐项目复制约定、手写配置 JSON 或选择内部 ID。

首次连接时明确说明：只自动接入用户正在授权开展工作的目录，不扫描其他项目；用户可暂停某项目或本次任务的记录。这个选择保存在本工具配置中，避免每次任务重复确认。

Skill 可以被隐式选择，但不保证每轮都被调用；官方当前支持 `SessionStart`、`Stop` 等 hooks，非托管 hook 首次及定义变化后需要信任。因此自动记录须同时具备工作约定、可靠记录入口和遗漏检查，不能仅凭复制一个 Skill 显示“全自动完成”。[Skill 文档](https://learn.chatgpt.com/docs/build-skills)、[Hooks 文档](https://learn.chatgpt.com/docs/hooks)

### 日常阅读

| 平台 | 默认入口与流程 | 异常或受限环境 |
| --- | --- | --- |
| Windows | 图形窗口打开“最新进展”，点击阶段查看完成、验证、阻塞、下一步和本次文件 | 文件不可用时保留原位置及原因；设置与来源配置留在高级入口 |
| Linux | 拟议 `handoffdesk tui`，直接在本机终端或 SSH 中浏览、搜索、阅读历史和文本附件 | 无 TTY、`TERM=dumb` 或依赖缺失时给出普通文本/CLI 入口，不尝试启动 Tk 或 X11 |

两种阅读端使用相同语义，每台机器各自读取本机状态。Windows 安装不会自动获得 Linux 服务器的记录；首期不把 SQLite 放到共享网络目录，不承诺文件或记录跨机器同步。

## 3 自动接入与项目归属

新增 Workspace Module，外部 Interface 为 `inspect(cwd)`、`connect(path)`、`relocate(project_id, path)`；内部复用 [bootstrap.py](../../handoffdesk/bootstrap.py)、[registry.py](../../handoffdesk/registry.py) 与 [paths.py](../../handoffdesk/paths.py)。

- 优先匹配已登记的真实根目录；存在多个候选时使用明确的包含关系和已保存会话绑定，不按目录名、最近打开项目或 GUI 当前选择猜归属。
- 未登记的 Git 工作目录使用仓库顶层；Git worktree 通过 common-dir 关联同一项目，同时保存本次 checkout 标识。远程 URL 只作辅助信息，不能单独作为身份，也不能记录其中的凭据。
- 非 Git 项目使用当前任务明确指定的工作目录。默认不扫描父目录中的其他项目；monorepo 默认一个项目，主动拆分留给高级操作。
- 新项目生成稳定内部 ID，显示名称来自目录或任务语义。移动项目时通过显式重定位保留 ID，避免把路径哈希当作永久身份。
- 并发自动接入使用跨进程注册锁；取得锁后重新读取、合并并校验配置，再原子替换。冲突时重读重试，确保两个 Agent 注册不同项目都能保留；残留锁只有确认所有权和进程状态后恢复，不能盲删。
- 新注册项目允许没有来源配置。Agent 的显式阶段附件即可完成交接；自动递归读取文件、生成 JSON Pointer 或配置复杂采集器不作为首次使用前提。
- 相同宿主会话恢复时复用持久工作线绑定；明确指定已有工作线时校验后使用。新任务无法可靠对应已有工作线时，自动建立按任务命名的独立工作线，不混入人正在阅读的工作线。纯问答不因此创建项目或空工作线。
- 子 Agent 默认向主 Agent 提供结果，由主 Agent 汇总阶段记录；独立交付确需单独记录时使用自己的任务绑定与提交令牌，不能共用主 Agent 的当前令牌。

## 4 将记录流程压缩成两个主要动作

新增 Recording Session Module，Agent 的主要 Interface 为 `begin`、`checkpoint`，另提供 `status` 和 `resume` 恢复查询；宿主 Adapter 使用下文的轮次处置与汇报确认 Interface。内部继续使用 [AgentRecords](../../handoffdesk/agent_records.py) 与 [Store.save_agent_record](../../handoffdesk/store.py)，保持记录和文件清单一次事务提交。

以下是拟议接口示意，不是当前可运行命令：

```sh
handoffdesk agent begin --cwd /workspace/project --task "完善导出"
handoffdesk agent checkpoint --session SESSION --checkpoint TOKEN --stdin
handoffdesk agent status --session SESSION
```

`begin` 返回 `session_ref`、当前任务的相关历史、固定项目/工作线、`checkpoint_token`。宿主会话标识仅在真实可得时使用；否则生成并明确标为 HandoffDesk 自己的会话标识。压缩、恢复和 fork 的绑定规则由 Codex Adapter 处理，不能靠模型记住临时变量。

Agent 只填写语义内容，技术字段由 Module 补齐：

```json
{
  "kind": "handoff",
  "title": "导出补充阶段文件",
  "actual_done": "已完成的动作、结果与限制",
  "next_action": "下一位可以直接执行的第一步",
  "blockers": [],
  "verification": {"status": "partial", "summary": "实际检查范围及尚未验证内容"},
  "files": [{"path": "docs/result.md", "purpose": "本阶段结果和已知限制"}]
}
```

协议号、项目/工作线、作者身份、当前 revision、operation ID、绝对路径转换和回执回读由程序处理。相对附件路径以绑定的工作目录解析，仍执行现有存在性、重复、重定向和路径类型检查；不得自动将整个仓库作为附件。

`kind` 默认 `handoff`，表示实际形成的交接；`plan` 表示未来安排，此时 `actual_done` 必须为空。两者映射到现有协议的 `event_kind`，不把计划自动转换成已完成工作。作者身份只取真实宿主提供的信息，未知值不猜测。

### 提交状态与恢复

1. `begin` 或前一次成功回执提供一个令牌。发送前持久化令牌、规范化原请求、operation ID 和基准 revision。
2. `checkpoint` 内部校验、保存、按回执核对记录与文件，成功后返回稳定 `record_id`、`node_id`、文件数、`replayed`、人可读汇报句及下一个令牌。普通调用者无需额外执行 validate/files。
3. 响应丢失或进程中断时，用同一令牌和原请求重试。不能为每次网络/进程重试重新生成 operation ID；同令牌不同内容必须拒绝。
4. 冲突返回当前记录和原提案，Agent 阅读、比较并形成新的逻辑提交；新令牌只能在明确处理冲突后签发。禁止静默增加 expected_revision 强行提交。
5. 保存与“已向用户汇报”分开记录。数据库提交成功但聊天消息尚未发送时标为 `report_pending`；恢复时补报原记录，不生成重复交接。
6. 状态查询可以核对任何已发放令牌。失败返回稳定错误码、是否可原样重试、已知保存状态和下一步动作；不可确认是否保存时返回“待核对”，不能宣称成功或随意重新创建记录。

拟议错误码至少覆盖 `state_unavailable`、`permission_required`、`project_ambiguous`、`session_unknown`、`attachment_missing`、`operation_mismatch`、`revision_conflict`、`retry_pending`。新机器接口统一 JSON；旧协议接口保持兼容。

### 轮次处置和汇报确认契约

为了让结束检查有可靠依据，再提供三个由 Adapter 调用的小 Interface；它们不要求用户输入参数，也不新增阅读时间线记录：

| Interface | 写入及检查规则 |
| --- | --- |
| `observe_turn(host_context)` | 建立轻量 `session_ref/turn_ref`，暂不注册项目或工作线。真实宿主 ID 可得时才使用；否则返回明确属于 HandoffDesk 的标识。纯问答因此可以被处理而不创建空项目。 |
| `conclude_turn(turn_ref, outcome, receipt_ids, reason)` | `outcome` 为 `recorded/no_record/paused/interrupted/failed`。`recorded` 必须引用已提交回执；`no_record` 要有明确原因，不能掩盖待保存成果、失败提交或漏报。按轮次幂等保存，冲突处置拒绝静默覆盖。Skill 可通过拟议 CLI `handoffdesk agent conclude --session … --outcome no_record --reason …` 表达无须记录，Adapter 负责绑定当前轮次。 |
| `ack_report(turn_ref, receipt_id, evidence_type, evidence_ref)` | 检查回执属于该轮次或其恢复链。`evidence_type` 区分宿主观察到的最终消息 ID 汇总与 Agent 自报；重复确认幂等。没有证据仍为 `report_pending`，只收到自报则为 `agent_acknowledged`，宿主看到最终汇总则为 `observed_in_final`。 |

这些状态都不表示用户已经看到或阅读消息。若宿主只提供最后一条助手消息，程序只能核验最终汇总，不能据此证明每次中途汇报都及时发生。实际即时性由端到端交互证据验收；能力不足时显示该限制。中断发生在保存与汇报之间时，保留 `report_pending`，恢复后补报原保存时间。

Stop 的补救预算绑定原始 `turn_ref` 并持久化，续跑产生的新宿主轮次要关联回原始轮次，不能因换了 ID 再次获得无限补救。只有完成受控宿主探针，才启用相应的自动确认能力。

## 5 何时记录以及如何汇报

| 情况 | 应有行为 |
| --- | --- |
| 完成可交接成果、形成重要决策、发现阻塞 | 当阶段立即 checkpoint，不等整段长任务结束 |
| 形成后续计划 | 使用计划语义；未来事项不得写成“已完成” |
| 研究或设计任务已有可复用产物 | 记录实际形成的结论、依据与产物，并区分建议和已实现能力 |
| 纯问答、重复状态查询、没有实质进展 | 只保存内部 `no_record` 处置及原因，不往阅读时间线灌空记录 |
| 用户明确暂停记录 | 尊重本次/项目范围，结束检查识别此状态 |
| 中断或崩溃 | 保留最近已确认记录与未完成提交，不从残缺信息生成完成事实 |

每次确认成功后，Agent 立即在当前对话发送一行，例如：“已记录『导出补充阶段文件』，记录 A，附件 1 项；已验证范围为……，下一步……。”原样重试的回执用“已确认先前记录 A”表述。任务结束时汇总本轮记录 ID 和任何未保存/未汇报项。

程序生成汇报句是为了减少遗漏，不替 Agent 生成成果事实。`verification` 明确是记录者报告，不把保存成功解释为产品自行重跑验证。`passed` 必须有实际检查范围；未提供验证时默认 `not_run` 并显示“未报告验证”，不能自动推定通过。来源快照仅在 Agent 明确核查后绑定，未知时保持空值。

Codex 接入使用以下拟议流程：

- `SessionStart` 提供短上下文与入口；恢复时找回绑定和未汇报回执。
- Skill 指导阶段保存与即时汇报。优先安装在用户级，避免每个仓库复制大段约定。
- `Stop` 按宿主 session/turn 检查本轮是否已有 checkpoint 或合法 `no_record`，并检查可得的汇报证据；最多请求一次补记或补报。再次失败时明确显示未完成状态，不能无限续跑。
- `Interrupt`/`SessionEnd` 只保存最小恢复信息；不依赖会话结束时可能被取消的后台任务保存唯一副本。
- 不解析不稳定的全量聊天转录来推定事实。若宿主只能观察最后一条助手消息，则用最终 ID 汇总核验；中途汇报的验证能力应单独标注。Agent 自报已发送只能叫“Agent 已确认”，不能假称程序证明消息已送达用户。

官方公开插件目录目前不接受包含生命周期 hooks 的提交。首期完整接入通过受支持的本地安装方式分发；公开 Skill/插件包可作为能力较弱的兼容入口，页面明确区别。不能把依赖 hooks 的首发计划建立在公开目录一键生效上。[插件提交限制](https://developers.openai.com/plugins/deploy/submission)

## 6 Windows GUI 与 Linux TUI 的阅读设计

### 共用 ReaderModel 与 ProgressFeed

新增 `progress_feed.py` 和 `reader_model.py`，提供 `changes(cursor)`、`list_records(filter, cursor, limit)`、`read(record_id)`、`ack(record_ids)`、`preview(file_id, limits)`。GUI/TUI 只负责交互和显示，不各自复制记录筛选、已读与附件规则。

- Feed 同时检测配置指纹和记录事件；新项目、任务与记录自动出现在列表中。
- 首页围绕阶段记录：标题、实际完成、验证范围、阻塞、下一步、本次文件、作者与时间。来源与变化复核保留为高级功能，不挡住普通阅读。
- 新记录增量进入列表，正在看的旧详情及滚动位置保持；用户可明确跳到最新。
- 已读按阅读者、项目/工作线和记录身份保存。`ack(record_ids)` 是幂等集合合并，打开最新记录不能清除较早未读。另提供显式“全部标已读/截至此处已读”。GUI/TUI 并发更新用事务合并，不使用整体覆盖嵌套字典的偏好写法。
- 记录查询分页，启动不读取全部历史。初始每页 50 条；项目统计使用有索引的摘要查询，性能以固定数据集测量。
- 阅读操作不自动采集项目来源、不保存新进度、不确认草稿。需要刷新来源时由高级操作明确触发。
- 导出同一 ReaderModel：包括作者、验证状态/范围、实际完成、下一步、本次文件名称/用途/位置，明确文件内容没有随摘要打包。

### Windows

用 HTML/CSS/JavaScript 构建本地阅读前端，以 pywebview 的 Windows WebView2 窗口承载；保留 Python 业务内核和 SQLite，不要求云服务、账号或网络。第一版使用浏览器原生模块与本地静态资源，避免用户安装 Node 或构建前端。后续复杂度需要时再引入 TypeScript 构建。Tk 入口仅保留为显式兼容入口，Windows 默认启动新窗口。

默认“最新进展”：项目导航、阶段列表、完整详情三栏，窄窗口折叠为可切换视图；标题、中文正文、路径和用途自然换行，不用固定字符数猜测高度。详情展示完成、验证、阻塞、下一步和本次附件，附件提供只读预览、打开、定位、复制完整路径和导出。深浅层次、间距、字号、焦点样式统一。先验证首页、详情、附件三个实际页面，再完成边界状态和无障碍检查。

原生窗口仅开放明确的 ReaderModel 方法；页面不接受任意文件路径或命令，不执行记录中的 HTML。开发用浏览器预览只监听回环地址，随机令牌与来源校验限制本机接口访问，关闭后停止服务。静态资源随包分发，不加载 CDN。新记录更新列表但不替换正在阅读的详情或滚动位置。

用原生文件关联打开文档、定位文件；脚本仍按只读文本展示。安装包提供桌面/开始菜单入口及“连接状态”，无需另开命令行设置路径。必须在 Windows 真机验证中文路径、缩放、文件打开、升级和卸载。

### Linux

优先选择 Textual，D0 先验证中文宽度、SSH、窗口缩放和键盘导航，再固定依赖版本。Textual 提供布局、输入和无界面交互测试，减少自行维护 curses 焦点与滚动逻辑；纯 CLI 保留。浏览器方案需要额外服务、端口和远程访问流程，暂不作为默认入口。[Textual 官方说明](https://textual.textualize.io/)、[测试接口](https://textual.textualize.io/guide/testing/)

宽屏显示“阶段列表—详情”两栏，80×24 切换列表/详情两屏。拟议按键为上下或 `j/k` 浏览、`Enter` 详情、`Esc` 返回、`/` 搜索、`p` 项目筛选、`f` 文件、`r` 刷新、`?` 帮助、`q` 退出；输入框中不得抢占普通字母。

TUI 在构造 `Service` 前检查 TTY 与依赖，失败时清楚退回 CLI。记录 CLI 不导入 Textual 或 Tk。每个查询 worker 使用自己的 SQLite 连接，结果通过消息进入 UI；过期搜索不能覆盖新条件，退出后终端状态恢复。

文本附件通过独立的有界读取接口预览，不调用会启动 Tk/xdg 的 `NodeFiles.open`。初始限制 1 MiB、2,000 行，超限明确截断；转义控制字符，不执行脚本。图片、PDF、模型等显示位置和状态，首期不做终端渲染。

SSH 中路径属于服务器。复制采用终端支持的能力并保留可选择的完整文本；不能把服务端剪贴板写入当成用户电脑已收到。只有明确具备本机桌面能力时才显示外部打开入口。[Textual 剪贴板说明](https://textual.textualize.io/api/app/#textual.app.App.copy_to_clipboard)

## 7 安装 状态定位与兼容迁移

统一安装登记保存运行程序、版本、状态目录、连接能力和本工具管理的文件清单，提供 `installation_id` 与 `state_id` 供阅读端和 Agent 核对。GUI、TUI、CLI、Skill、hooks 从同一登记解析状态位置，优先级保留为显式 `--app-dir`、`HANDOFFDESK_HOME`、安装登记、平台默认目录。隔离试验仍可显式覆盖，界面显示正在读取的机器与状态标识。

“连接 Codex”必须幂等：检查已有内容，只增删本工具拥有的条目，写前备份，失败回滚，卸载仅撤销接入和程序，不删除记录。hook 定义变化后如需重新信任，显示待处理状态，不借升级绕过宿主流程。首期不默认覆盖全局或项目 `AGENTS.md`。

健康检查须由真实 Agent 权限环境调用受控探针：读取配置、在目标状态内建立并移除临时文件、使用独立探针库执行 SQLite 事务、读回回执。探针不污染正式时间线。安装器自身的文件权限检查只能作为预检，不能证明受限 Agent 可用。

Windows 包含 Python、pywebview 与本地前端；安装器检测 WebView2 Runtime，按分发模式安装官方在线引导程序或离线运行时，不能把安装了 Edge 浏览器视为运行时存在。Linux 用户级包包含记录 CLI、TUI 及固定依赖，不要求 X11，不修改系统 Python。开发安装保留可选 extra。签名/校验、依赖许可证、升级失败回退属于发布验收；macOS 和未测架构不提前列为支持平台。[pywebview 架构](https://pywebview.flowrl.com/guide/architecture.html)、[WebView2 分发](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)

数据演进采用明确的新 schema 版本，建议在现有版本 4 之后增量新增：会话绑定、checkpoint 请求与回执、turn 处置、进度事件索引、逐记录已读状态。记录写入、回执归属与事件索引在同一事务提交；待提交原请求先单独持久化，再执行保存事务。配置文件热更新通过独立配置指纹确认，不假定它与 SQLite 同事务。

这要求在 Store 内提供一次事务完成上述写入的入口，复用原来的版本和幂等检查；不能先调用已有保存接口提交记录，再用另一个独立事务写回执，却声称二者原子。进程在任何一步中断后，恢复查询必须能判定“尚未提交”或“已提交并可重建回执”。

迁移前使用 SQLite backup API 生成一致副本并复制配置；事务内建表与索引，不重写原有 handoff payload、文件清单和各类 ID。迁移中断可重跑；失败回到旧副本。旧协议 1 的 Agent 继续调用新版兼容入口，但旧 0.9 程序不能写升级后的唯一数据库；现有 Store 对更高版本已有拒绝降级保护。回滚程序时使用对应备份，不能偷偷降低 `user_version`。

确定性用例要求零误归属、零重复提交、零历史覆盖、零虚假成功。自然语言触发另建至少 30 类真实任务提示、每类三次的评估集，覆盖实现、排错、研究、文档、纯问答和中断；在声明支持的完整 Codex 接入模式中，初始目标为至少 95% 适用任务在一次有限补救内完成“实际成果—保存—汇报”闭环，分别报告完成率、漏记率和漏报率。其余失败必须可见并分类，不能被计为无需记录或从分母删除。中断后恢复补报须注明原保存时间，不计为当时及时汇报。Skill-only 单独报告，不与完整接入混算。

读写正确性优先于平均耗时。为 1,000/10,000 条记录数据集测启动、首屏、筛选、增量提示及内存，固定测试机器与环境后再设发布性能预算；不把尚未实测的 Textual 或 SQLite 性能写成承诺。

## 10 本期范围与完成定义

本期保留现有记录协议、文件关联、只读来源和冲突语义；新增低配置接入、可靠提交/汇报恢复、双平台阅读和可安装分发。不会通过全量聊天采集、全盘目录扫描、自动执行项目脚本或共享网络 SQLite 来实现“自动化”。
